
## Deploy (2 minutes)

**Vercel / Netlify:** drag the folder into the dashboard, or:
```bash
npx vercel --prod
```
**GitHub Pages:** push this folder to a repo and enable Pages on the `main`
branch (root). No build step needed — it's plain HTML/CSS/JS.

## Features implemented against the brief

- **Format A — Profile Frame**: circular photo, gradient ring, curved
  `HH GOA 2026` / `#FrameInGoa` type, builder stamp.
- **Format B — Builder ID Card**: photo + Name + Role/Stack + Builder Title
  on a boarding-pass-style card, with auto-shrinking text so long names still fit.
- **JPG / PNG / HEIC**: HEIC (iPhone default) is converted client-side via
  `heic2any` before it ever touches a canvas.
- **Smooth auto-fit for any photo shape**: portrait, landscape, or odd aspect
  ratios are "cover"-fit into the frame; a zoom slider + drag-to-reposition
  lets people fine-tune the crop.
- **Download**: canvas → PNG via `toDataURL`/`toBlob` and an `<a download>` link.
- **Share to X**: on mobile, uses the Web Share API (`navigator.share` with a
  `File`) so the actual badge image attaches to the share sheet directly —
  this is the modern replacement for the old "text-only" tweet intent, since
  X's web intent URL cannot attach an image on its own. Desktop browsers
  (and any browser without file-sharing support) fall back to downloading the
  PNG and opening a pre-filled `twitter.com/intent/tweet` tab with the
  `#FrameInGoa` caption, same as the brief's Step 3.
- **Mobile-first**: single-column layout under 860px, touch drag for
  repositioning, large tap targets.

## Optional: dynamic OG image previews (Step 4 in the brief)

Right now `og:image` points at one static `assets/og-default.png`, so a link
to the site shows a generic preview card. If you want *each person's own
badge* to show up as a live image preview when their link is shared on X,
that does require a tiny backend, exactly as the brief describes — the
client-side approach can't host a per-user image at a stable URL on its own.

Minimal version of that flow:

1. On "Share", `POST` the canvas `toDataURL()` output to a backend endpoint.
2. The backend decodes the base64 PNG, saves it to storage (e.g. Django
   `ImageField`, or S3), and returns a short URL like `/badge/<id>/`.
3. That route renders a tiny HTML page whose `og:image` points at the saved
   file:

   ```html
   <meta property="og:title" content="HH Goa 2026 Builder Badge" />
   <meta property="og:image" content="{{ badge.image.url }}" />
   <meta name="twitter:card" content="summary_large_image" />
   ```

4. Share *that* URL instead of (or alongside) the raw image — X will crawl it
   and show the person's actual badge as the big preview card.

This is additive: the rest of the app (upload, compositing, download, direct
image share) keeps working with zero backend, so it's safe to ship without
this and add it later if there's time before the deadline.
